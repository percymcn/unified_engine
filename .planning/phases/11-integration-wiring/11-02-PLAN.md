# Plan 11-02: Wire Webhook Router to Hexagonal Architecture

## Overview

The webhook router currently imports and uses the old `SignalProcessor` service. This plan migrates it to use `ProcessSignalUseCase` from the DI container, enabling the hexagonal architecture for signal processing.

## Gap Being Closed

From MILESTONE-AUDIT.md:
- "Webhook router uses OLD SignalProcessor instead of ProcessSignalUseCase"
- "Signal Processing: Breaks at webhook → uses old service layer"

## Current State

```python
# app/routers/webhooks.py (lines 59-68)
from app.services.signal_processor import SignalProcessor

@router.post("/tradingview")
async def handle_tradingview_webhook(...):
    processor = SignalProcessor()
    result = await processor.process_signal(signal_data, db)
```

## Target State

```python
# app/routers/webhooks.py
from fastapi import Depends, Request
from app.dependencies import get_container

@router.post("/tradingview")
async def handle_tradingview_webhook(
    request: Request,
    ...,
):
    container = get_container(request)
    use_case = container.process_signal_use_case()
    result = await use_case.execute(signal_command)
```

## Tasks

### Task 1: Update Imports
- Remove: `from app.services.signal_processor import SignalProcessor`
- Add: `from app.dependencies import get_container`
- Add: `from app.application.use_cases.process_signal import ProcessSignalCommand`

### Task 2: Migrate /tradingview Endpoint
- Get container from request: `container = get_container(request)`
- Create use case: `use_case = container.process_signal_use_case()`
- Build command from webhook payload:
```python
command = ProcessSignalCommand(
    source="tradingview",
    symbol=payload.symbol,
    action=payload.action,
    # ... map all fields
)
```
- Execute: `result = await use_case.execute(command)`

### Task 3: Migrate /trailhacker Endpoint
- Same pattern as tradingview
- Map TrailHacker-specific payload fields to command

### Task 4: Migrate /custom Endpoint
- Same pattern for custom webhooks
- Handle flexible payload mapping

### Task 5: Update Response Mapping
- Map use case result (domain object) to API response
- Maintain backward-compatible response schema

### Task 6: Keep Old Processor as Fallback (Temporary)
- Add feature flag: `USE_HEXAGONAL_SIGNALS = True`
- If False, fall back to old SignalProcessor
- Remove after verification

## Domain Layer Integration

The signal processing now flows through:
1. **Webhook Router** → receives HTTP request
2. **ProcessSignalUseCase** → orchestrates business logic
3. **SignalEntity** → validates signal data
4. **BrokerPort** → adapter executes trade
5. **EventPublisher** → publishes SignalProcessed event
6. **WebSocket** → notifies UI of update
